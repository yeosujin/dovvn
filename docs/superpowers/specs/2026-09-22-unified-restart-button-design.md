# 업데이트 통합 확인과 재시작 버튼 설계

## 배경

`2026-09-21-auto-restart-after-update-design.md`(이하 이전 스펙)에서 두 업데이트 모두 업데이트 직후 다운로드가 끝나면 자동으로 종료→재시작되도록 만들었다. 그 결과 현재 상태는 다음과 같다.

| 업데이트              | 자동 확인                                                   | 재시작                          |
| --------------------- | ----------------------------------------------------------- | ------------------------------- |
| 앱 (electron-updater) | 시작 시 + 6시간마다 (`appUpdateStore`)                      | 다운로드 완료 후 큐가 비면 자동 |
| yt-dlp (`yt-dlp -U`)  | 없음. 설정 패널의 "업데이트 확인" 버튼을 눌러야만 확인·설치 | 버전이 바뀌면 큐가 비면 자동    |

상단 필(`UpdatePill.tsx`)은 앱 업데이트 상태만 반영하고, 클릭할 수 없는 단순 표시다. (v2.3.1 이전에는 여기에 클릭 가능한 "업데이트 설치" 버튼이 있었지만, 이전 스펙에서 자동 재시작으로 바꾸며 제거했다.)

사용자가 원하는 것: yt-dlp도 앱처럼 자동으로 주기 확인하고, 둘 중 하나라도 재시작 대기 중이면 상단에 클릭 가능한 버튼이 뜨게 한다. 자동 재시작(다운로드가 끝나면 알아서 재시작)은 그대로 두고, 이 버튼은 "더 기다리지 않고 지금 바로" 재시작하는 수동 경로를 추가한다.

## 확정된 결정

1. yt-dlp 업데이트도 앱과 같은 주기(시작 시 + 6시간마다)로 자동 확인한다.
2. 자동 재시작은 그대로 유지하고, 상단에 수동 "지금 재시작" 버튼을 추가한다.
3. 버튼을 누르면 진행 중인 다운로드를 모두 취소하고 즉시 재시작한다. 이미 받은 데이터는 사라진다.
4. 진행 중인 다운로드가 있을 때는 확인 다이얼로그 대신 버튼에 툴팁(또는 그에 준하는 문구)으로 "중단된다"는 사실을 알린다.

## 설계

### 1. 재시작 대기 상태를 단일 출처로 통합

앱 업데이트와 yt-dlp 업데이트 중 무엇이 재시작을 요청했는지는 UI 입장에서 중요하지 않다. 실제로 다운로드를 막고 재시작을 미루는 값은 메인 프로세스의 재시작 스케줄러(`src/main/restartScheduler.ts`, `src/main/restart.ts`)가 이미 갖고 있는 `pending` 하나뿐이다. 이 값을 그대로 렌더러에 내보내는 것이 두 스토어의 상태를 렌더러에서 다시 조합하는 것보다 정확하다 — 창을 닫았다 다시 열어도(맥OS는 창을 닫아도 프로세스가 남는다) 메인에 물어보면 최신 값을 알 수 있기 때문이다.

**`src/main/restartScheduler.ts`** (기존 파일, 순수 로직 — 기존 10개 테스트는 그대로 통과해야 한다):

- `RestartSchedulerDeps`에 선택적 `onPendingChange?: (pending: boolean) => void`를 추가한다.
- `pending`이 실제로 바뀌는 두 지점에서만 호출한다.
  - `requestRestart`에서 `pending = true`로 바뀌는 순간 (요청이 처음 들어올 때 한 번뿐이다 — 이미 대기 중이거나 큐에 저장된 요청이 있으면 이 줄에 도달하지 않는다).
  - `execute`에서 `run()`이 `false`를 반환해 `pending = false`로 바뀌는 순간.
- 새 훅을 검증하는 테스트 2개를 추가한다: 즉시 실행 시 `true`로 한 번 불리는지, 실패로 해제될 때 `false`로 한 번 불리는지.

**`src/main/restart.ts`** (기존 파일): 스케줄러가 부르는 단일 콜백을 리스너 배열로 팬아웃하고, 새 함수 `onRestartPendingChange(listener)`를 내보낸다. (`queue.ts`의 `onIdle` 리스너 배열과 같은 패턴.)

**`src/main/ipc/restart.ts`** (신규): 다른 IPC 모듈(`ipc/appUpdater.ts`, `ipc/download.ts`)과 같은 형태로 `registerRestartIpc()`를 내보낸다.

- `onRestartPendingChange`로 받은 값을 모든 창에 `restart:pending-changed`로 브로드캐스트한다.
- `ipcMain.handle('restart:is-pending', () => isRestartPending())` — 렌더러가 마운트될 때 현재 값을 한 번 조회하기 위한 것. 창이 닫혀 있던 사이에 재시작이 요청됐다가 대기 중인 상태를 새로 열린 창이 알 수 있게 한다.
- `src/main/index.ts`에서 `registerUpdaterIpc()`, `registerAppUpdaterIpc()`보다 먼저 등록한다. 두 모듈 다 시작 직후 `requestRestart`를 부를 수 있어서, 리스너가 그보다 늦게 등록되면 첫 변화를 놓칠 수 있다.

### 2. yt-dlp 자동 확인 (메인 프로세스)

**`src/main/ytdlp/updater.ts`** 수정:

- `registerUpdaterIpc()`에 시작 시 1회 + 6시간마다 `update()`를 조용히 호출하는 타이머를 추가한다. 실패는 무시하고 다음 주기에 재시도한다(기존 앱 업데이트의 조용한 주기 확인과 같은 태도).
- **동시 실행 방지.** 자동 확인과 설정 패널의 수동 "업데이트 확인" 버튼이 겹치면 `yt-dlp -U`가 같은 바이너리에 두 번 실행될 수 있다. `update()`를 진행 중이면 같은 Promise를 반환해 두 번째 호출이 같은 결과를 기다리게 한다. (기존에도 잠재된 문제였지만, 자동 확인이 생기면서 실제로 일어날 가능성이 커져 함께 고친다.)
- 이 변경은 `update()`의 반환 타입을 이름 있는 타입(`UpdateOutcome`)으로 추출하는 정도만 건드리고, 함수 본문(버전 비교, 재시작 요청 로직)은 그대로 둔다.
- 메인 프로세스 안에서 도는 타이머이므로 창이 닫혀 있어도 계속 동작한다. (앱 업데이트의 주기 확인은 렌더러 쪽 타이머라 창이 닫히면 멈춘다 — 기존 동작이고 이번에 고치지 않는다.)
- **자동 확인 중이라는 표시는 상단 필에 두지 않는다.** 앱 업데이트의 조용한 주기 확인(`check(true)`)이 아무것도 찾지 못하면 필에 아무 표시도 안 남기는 것과 같은 태도다. 렌더러는 이 확인이 진행 중인지 알 필요가 없고, 결과로 재시작이 필요해졌을 때(`restart:pending-changed`)만 반응한다.

### 3. 렌더러: 통합 스토어

**`src/renderer/src/stores/restartStore.ts`** (신규):

```ts
interface RestartState {
  pending: boolean
  forcing: boolean
  init: () => void
  forceRestart: () => Promise<void>
}
```

- `init()`: `window.api.isRestartPending()`으로 초기값을 받고, `onRestartPendingChanged`를 구독한다. 값이 `false`로 바뀌면 `forcing`도 함께 `false`로 되돌린다(앱 업데이트 설치가 실패해 대기가 풀렸는데 `forcing`만 계속 켜져 있는 경우를 막기 위해).
- `forceRestart()`: **새 IPC를 만들지 않는다.** `useDownloadStore`에서 상태가 `queued` 또는 `downloading`인 항목을 모두 찾아 기존 `window.api.cancelDownload(id)`를 호출한다. 취소되면 큐가 비고, 메인의 재시작 스케줄러가 (이미 검증된 경로로) 자동으로 재시작을 실행한다. 취소 요청 자체는 빠르게 끝나므로(`ipcMain.handle('download:cancel', ...)`가 프로세스 종료를 기다리지 않는다) `forcing`은 실제 재시작이 일어날 때까지 계속 켜져 있다가, 재시작이 성사되면 앱이 종료되며 화면이 사라진다.

`App.tsx`의 기존 초기화 `useEffect`에 `restartStore.init()` 호출을 추가한다.

### 4. UI

**`src/preload/index.ts`**: `isRestartPending`, `onRestartPendingChanged` 두 항목을 기존 컨벤션(`VersionResult`류 타입, `subscribe<T>` 헬퍼)대로 추가한다.

**`src/renderer/src/components/UpdatePill.tsx`** 전면 수정:

- `restartStore.pending`이 `true`면 클릭 가능한 버튼을 보여준다. `onClick={forceRestart}`, `disabled={forcing}`. 버튼 문구는 세 단계다: 강제 재시작 진행 중(`forcing`)이면 "재시작 중…", 진행 중인 다운로드가 있으면 "지금 재시작 (다운로드 N개 중단)", 없으면 "지금 재시작". 아이콘은 `forcing` 동안 `animate-spin`으로 돈다(스피너 상태와 같은 시각 언어로 통일).
- 진행 중인 다운로드가 있으면 `title` 툴팁으로도 "진행 중인 다운로드 N개가 중단돼요"를 붙인다(문구가 버튼에 이미 나와도 호버 시 전체 문장을 다시 보여준다). 없으면 툴팁 없이 바로 누를 수 있다.
- `pending`이 아니고 앱 업데이트가 `checking`/`available`/`downloading`이면 기존처럼 "버전 확인 중…" 스피너를 보여준다. (`downloaded` 단계는 이제 항상 `pending === true`와 거의 동시에 겹치므로 이 분기에서 뺀다 — 클릭 가능한 버튼이 먼저 그려진다. 최종 리뷰에서 이 조건이 코드에 남아 있던 것을 발견해 정정했다: 남아 있으면 앱 업데이트 설치 직후 한 프레임, 그리고 설치 파일 준비 실패로 `pending`만 풀리는 드문 경로에서는 영구히 "버전 확인 중…"이라는 잘못된 문구가 표시된다.)
- 그 외에는 `null`.

**설정 패널은 건드리지 않는다.** 앱/yt-dlp 각각의 수동 "업데이트 확인" 버튼과 문구는 그대로 유지한다. 상단 버튼은 추가되는 것이지 기존 수동 경로를 대체하지 않는다.

## 에러 처리와 엣지 케이스

- **강제 재시작 중 다운로드가 이미 자연스럽게 끝난 경우**: `cancelDownload`가 이미 없는 id에 대해 `{ ok: false }`를 반환할 뿐 예외는 아니다. 큐는 어차피 비워지는 중이라 재시작에 영향 없다.
- **`pending`이 됐다가 이유 없이 `false`로 풀리는 경우**(예: 앱 업데이트 설치 파일 준비 실패): 버튼이 사라지고, `forcing` 중이었다면 함께 꺼진다. 사용자는 버튼이 사라진 이유를 알 수 없지만, 이전 스펙에서 이미 짚은 한계다(설정 패널에서만 사유 확인 가능).
- **자동 확인과 수동 확인이 겹침**: `update()` 동시 실행 방지로 같은 결과를 공유한다. 설정 패널의 "확인 중" 스피너는 사용자가 직접 누른 시점부터 시작되므로, 이미 진행 중이던 자동 확인이 곧 끝나면 스피너가 예상보다 빨리 사라질 수 있다. 사소한 동작이라 손대지 않는다.
- **두 업데이트가 동시에 재시작을 요청**: 이전 스펙대로 앱 업데이트가 우선한다(스케줄러의 기존 규칙, 변경 없음).

## 범위 밖 (알려진 한계)

- 창을 완전히 닫아둔 사이에는 앱 업데이트 주기 확인이 멈춘다(렌더러 타이머라서). yt-dlp 쪽은 메인 타이머라 이 한계가 없다. 기존 비대칭이고 이번에 통일하지 않는다.
- "지금 재시작" 버튼을 눌렀을 때 취소되는 다운로드 목록은 되돌릴 수 없다. 확인 다이얼로그 없이 버튼 문구와 툴팁 경고만 제공한다(사용자 결정).
- 이전 스펙의 알려진 한계(앱 업데이트가 yt-dlp를 번들 버전으로 되돌릴 수 있음, 자동 설치 실패가 상단에 표시되지 않음 등)는 그대로 유효하다.
- **yt-dlp 버전 조회와 자동 확인의 경합.** `yt-dlp -U`로 바이너리를 교체하는 도중에 `ytdlp:version`(설정 패널이 버전을 표시할 때 호출)이 같은 바이너리를 실행하면, 교체 중인 파일이 일시적으로 실행 불가능한 상태라 파이썬 트레이스백이 그대로 노출될 수 있다. 이 두 함수(`getVersion`/`tryGetVersion`)는 이번 변경에서 건드리지 않은 기존 코드지만, 자동 확인이 매 실행마다 조용히 돌면서 겹칠 가능성이 실제로 커졌다(이전에는 설정 패널에서 수동으로 누를 때만 `-U`가 돌았다). 최종 결과(설치된 버전)는 영향받지 않는다 — 패키징 빌드 스모크 테스트로 6회 재현했을 때 모두 최종 버전은 정상이었다. 고치려면 `ytdlp:version` 핸들러가 `update()`의 진행 중 여부(`inFlightUpdate`)를 확인해 진행 중이면 조회 대신 안내 메시지(설정 패널에는 이미 "다시 시도" 버튼이 있다)를 반환하면 되지만, 이번 범위에서는 다루지 않는다.
- **첫 실행 시 짧은 다운로드 차단 창.** yt-dlp 자동 확인이 앱 업데이트와 "같은 주기"라고 표현했지만 첫 실행 시 체감은 다르다. 앱 업데이트는 다운로드가 끝나야 재시작하지만, `yt-dlp -U`는 몇 초 안에 끝나고 큐가 비어 있으면 곧바로 재시작이 실행된다. 그래서 yt-dlp가 오래된 상태로 설치한 직후, 사용자가 몇 초 안에 다운로드를 시작하면 "재시작 대기 중이라 시작할 수 없어요" 오류를 보고 곧이어 창이 닫혔다 다시 뜨는 것을 겪을 수 있다. 검증 시나리오 1이 이 동작을 그대로 승인했고 스모크 테스트로 확인됐다 — 설계상 받아들인 것이지 결함이 아니다.

## 검증

- `npm run typecheck`
- 스케줄러 순수 로직: 기존 10개 + `onPendingChange` 훅 테스트 5개(초기 실행, 실패 해제, 예외 해제, 대기 후 실행, 훅 생략 시 안전성), Node 내장 `node --test`로 검증 (저장소에 커밋하지 않음).
- 패키징 빌드 스모크 테스트로 실제 검증한 시나리오:
  1. 다운로드 없이 앱 시작 → yt-dlp가 자동으로 확인·설치되고(직접 호출하지 않았는데도 반영됨), 곧 자동 재시작된다. 3회 재현.
  2. 다운로드 중 자동 확인 → 상단 버튼에 "지금 재시작 (다운로드 1개 중단)"이 실제 DOM에 그대로 렌더링됨을 확인. 새 다운로드는 차단 문구와 함께 거부됨.
  3. 그 버튼을 실제로 클릭(스토어 함수 직접 호출이 아니라 DOM `click()`) → 즉시 "재시작 중…"으로 바뀌고 비활성화됨. 약 2초 안에 재시작, 남은 yt-dlp 프로세스 없음.
  4. 다운로드가 없을 때 버튼 문구가 "지금 재시작"(개수 표시 없음)인 것을 확인.
  5. 자동 확인과 수동 확인이 겹쳐도(동시 실행 방지) 같은 결과를 공유하고 yt-dlp 프로세스가 두 번 뜨지 않음.
- 스모크 테스트로 검증하지 못한 것 (범위 밖으로 남김):
  - 6시간 주기 자체(세션 안에서 실제로 6시간을 기다릴 수 없다).
  - 앱 업데이트(electron-updater) 경로의 자동 재시작 — 실제 GitHub 릴리즈가 필요해 로컬에서 검증 불가.
  - 진행 중인 다운로드가 2개 이상일 때 버튼 문구(1개만 검증).
  - 창을 닫았다가(맥 Dock 아이콘으로) 다시 열었을 때 대기 상태가 새 창에도 보이는지 — `restart:is-pending` 조회가 이 경우를 위해 존재하는 유일한 목적이지만, 이 경로를 직접 실행한 증거는 아직 없다.
